Paper in preparation

An autonomously built composites database, and how to check it

Property data for fiber-reinforced composites sits mostly in research papers: in tables, in sentences and in plots. I built a service that reads the open-access literature and builds the database from it. It is one program on a scheduler, deployed on a Hugging Face Space and writing to PostgreSQL. No person selects, supplies or corrects a query, a document or a value.

One cycle of the service

  1. Discover. A discovery pass fills a queue of candidates from OpenAlex, Europe PMC, Semantic Scholar, arXiv, NASA's technical report server and vendor data-sheet pages. The queries come from a rotating set of seeds, a grid of fiber, matrix and property terms, and a language model.
  2. Download. Only open-access copies are read. Duplicates are removed by DOI, link and file hash, and a file is accepted only if it verifies as a PDF.
  3. Extract. Gemini reads the text of every page and returns each value as a row: material, grade, matrix, fiber, fiber fraction, property, value as printed, unit, test condition, page and quotation. Code then lists the numbers on each page that no row used, and a second request asks only about those. Values read off figures are stored as estimates.
  4. Check against the source. No model is involved. Each value is searched for on its cited page, and units are converted to SI and tested against wide ranges. A row that passes is called verified. That means it passed these checks, not that it is known to be correct.
  5. Store. A row that fails is stored with its reason and is never deleted.

How much of a paper it finds

The database held 81.6% of the labeled values (95% confidence interval 76.9 to 86.1%), and at least 74.0% once chance matches are subtracted. For a property in its vocabulary that a paper states in its own text or tables, outside long series, it held 95.5%. The single-pass extractor it replaced held 36.2% on the same PDFs.

This measures coverage, not correctness. The annotators recorded a median of 113 values per paper, and the database holds 231.

The idea of the paper

Checks that borrow their inputs

A check against the source has a blind spot. It passes any error that the source itself contains: a unit printed wrongly in the paper, or a number quoted from another specimen's row. To see those, a check has to compare the value with something outside the passage.

Composite mechanics offers such comparisons, because a composite's stiffness, strength and density are tied to those of its fiber and matrix. But a paper rarely reports every input. Only 2.6% of the composite moduli in the database come with their own paper's fiber and matrix moduli.

So the checks borrow. A knowledge graph, rebuilt from the database by rules alone, links each value to its material, fiber, matrix and grade. A check takes the inputs a paper lacks from other papers' verified records of the same constituents, and every flag cites the rows it used. There are four physical relations (a rule-of-mixtures bound on modulus, a density rule of mixtures, a strength cap, and the identity between weight and volume fraction) and a consensus check across papers. Borrowing lets each relation test 4.4 to 11 times as many values.

31,638 planted errors whose source agrees with the wrong value. Results of the draft of 16 Nov 2026.

The bounds are scored on composite tensile moduli and consensus on values compared across papers. The two language-model rows give both.

The language-model judge catches the most, but it rejects 10.5% of correct values and cites no evidence. Every flag from the graph names the papers and the rows it used.

Manufacturers' data sheets give an outside reference. Of 602 fiber values for named Toray and Hexcel grades, from 193 papers, 80% are within 10% of the manufacturer's number. Of the values the graph flags, 65% are more than 30% off, against 7% of the rest.

A blind human audit of 260 stored values is under way to measure correctness directly.

Manufacturing Intelligence Pipeline

Choosing how to make a polymer-composite part (injection molding, compression molding, thermoforming, filament winding and 13 other processes) is an expert decision governed by constraints. The pipeline makes that decision from a photo and shows its reasons. A vision-language model (VLM) reads the part. A rule engine, written from manufacturing textbooks and papers, turns what the model read into a ranking of the processes and lists the rules that moved each one up or down.

From photo to answer

  1. Detect and segment every component in a photo of a vehicle.
  2. Perceive. The VLM answers a fixed list of questions about each part: is it hollow, does it have ribs, are there undercuts, what is the production volume. It also gives its own shortlist of eight processes.
  3. Decide. The rule engine combines the answers and the shortlist into a ranking of the 17 processes.
  4. Explain. Each result lists the observations and the cited rules behind it, so a person can check the reasoning.

100 held-out photos, scored once in Oct 2026. Every setting was chosen on 535 development photos and frozen first. Labels are by part type; labels for each photo are in progress.

Where it stands

The benchmark is 635 openly licensed photos of real parts in 41 part categories. A part usually has about two correct processes. On the held-out photos the current design ranks a correct process first for 73% of photos and keeps every correct process in its top 8 for 88%. The first design reached 19% and 11%.

In the first design every rule was a veto, so one misread feature deleted the right answer. On 11 of 16 wound composite tubes the VLM reported ribs, probably the winding bands, and the no-ribs rules removed both correct processes. I rewrote the engine so that rules are evidence: each one moves a process up or down the ranking, and nothing is deleted. The rule base grew from 92 to 564 cited rules. I checked every rule I could against the development photos, and 142 point the right way.

The rule engine is now level with the VLM on the top pick, and it adds what the VLM cannot give: the rules behind every ranking. With 100 photos, differences of a few points are within noise.

Cross-validation on the 535 development photos, Oct 2026. Every photo is scored by a model that never saw it. The held-out photos have not been scored with this model yet.

Learning how far to trust each observation

Hand-set weights treat every observation as equally reliable, and they are not. The VLM's guess of production volume is useful. Its reading of wall thickness points the wrong way. So I let the development photos set one trust number for each perceived feature, about 22 learned numbers in all, while every rule keeps the direction it was written with.

This version is ahead of the VLM alone at keeping every correct process in the top 8: by 3.0 points on new photos (95% range 1.1 to 4.9) and by 2.6 points on part types it never saw (0.9 to 4.5). The top pick does not change. Giving every rule its own weight looked better on familiar parts and worse on unseen ones, which is memorizing part types, so I froze the simpler model.

A small open model, fine-tuned

I also fine-tuned a small open model on the development photos. On the held-out photos every correct process is in its top 8 for 73% of photos, against 40% for the same model without fine-tuning, and in its top 3 for 43% against 29%. Its top pick did not improve: it answers injection molding for 88 of the 100 photos. On part types it never saw, it is no better than guessing, and the much larger Gemini model still leads at 88%. Fine-tuning taught the small model which processes go together. It did not teach it to see them.

Simulation, Jul 2026. 150 photos, then 635 with a preregistered protocol, Aug 2026. Audit of the metric, Sep 2026.

How the design got here

I defended the first design at my preliminary exam. On a seeded benchmark of 1,000 instances, built from 14 expert-labeled components with simulated perception noise, it scored F1 0.385 on the hard cases, where injection molding is not the only answer. A simulated direct classifier with the model's bias scored 0.136, and the rules with perfect perception 0.510.

On real photos the result inverted. On the first 150 photos the vetoes collapsed to 0.086, and the record of observations showed where: 84% of the wrong eliminations came from two yes/no questions, whether the part is hollow (58%) and whether it needs continuous fiber (26%). I reworded the hollow question and preregistered the rerun on 635 photos, with the line that would count as success written down first. The pipeline rose to 0.198 (95% confidence interval 0.176 to 0.223). That is a real improvement, and it is under the 0.20 line I had set, so I reported it as a miss and changed the design.

Then I audited the metric. A predictor that always answers injection molding scores F1 0.555 on all 635 photos, so the number had no floor. I replaced it with the plain percentages above, always next to a guessing baseline.

The same runs show the model's bias. Asked for one answer, the VLM named injection molding for 71% of 150 photos, where surveyed experts chose it in 24% of their picks. Its shortlist of eight still held every correct process for 133 of the 150.

In progress

What comes next

More rules stopped helping because the questions were the weak point. The VLM said “continuous fiber” for 86% of injection-molded parts, which a photo cannot show, and when asked twice whether a part is hollow it changed its answer on 47% of photos.

The follow-up asks about marks a camera can see: a pinch-off seam means blow molding, layer lines mean 3D printing, ejector-pin marks mean injection molding. I set the bar before collecting any data: every correct process in the top 3 on at least 52% of held-out photos, against 47% for the VLM alone. Labels for each photo, instead of each part type, are being added to the held-out set.

Beyond this, I am starting to extend the pipeline to inverse design: inferring the manufacturing process from a material's microstructure.

Verification for a game simulator

A deterministic eight-player game simulator with a Python game core and a TypeScript combat engine. My part is showing that it is right.

  • I built the verification harness: a benchmark that replays recorded real fights, an auditor that recomputes every hit and attack timer from the rules, invariant, mirror and mutation checks, and CI.
  • The engine now calls the winner of 79.5% of 1,261 real fights, against 72.4% for a board-value baseline. Changes are gated on a paired no-regression test: exact McNemar on winner accuracy and a bootstrap on Brier score.
  • I set up and run the agent loop that drives the work. It runs the checks, files a ticket for each root cause, fixes tickets in parallel waves of coding agents, and gates each pull request on the checks. I review and merge what passes.
  • 32 pull requests so far, in a codebase of about 50,000 lines of Python and 35,000 lines of TypeScript with more than 1,400 tests.
